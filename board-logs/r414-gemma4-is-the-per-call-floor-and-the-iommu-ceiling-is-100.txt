1. ⛔ gemma4's EXTRA DISPATCHES ARE REAL AND THEY ARE NOT THE LOSS
---------------------------------------------------------------------
gemma-4-E2B is the model that lost the round of record: 8.91 tok/s against the
vendor's 9.23, -3.5%, clearing its own 0.6% spread. It is also the model with
the most NPU dispatches a layer, and the reason is architectural.

gemma3 runs seven projections a layer and pays FOUR fences, because matvec_pair
puts q, k and v in one submit and gate and up in another. gemma4 runs NINE --
its per layer embedding adds inp_gate (256 x 1536) and proj (1536 x 256) -- and
the two cannot pair, because proj reads what inp_gate wrote. Six fences a layer
against four. 35 layers, so 70 extra a token, for 27.5 MMAC of arithmetic.

At the fitted 78 us a call before a byte moves, that is 5.5 ms of a 112 ms
token. So: refuse a dispatch below a MAC threshold and let the CPU have it.

CHARSIU_NPU_MIN_MAC, tests/board_min_mac.sh, five alternating pairs, both arms
naming the knob:

    model              A (=0, ships)   B (=1000000)   margin   spreads
    gemma-4-E2B         9.56 tok/s      9.17 tok/s    -4.08%   0.84 / 2.29%
    gemma-3-1b         21.63           21.64          +0.05%   0.28 / 0.42%

⛔ 1) B LOSES BY 4.08%, WHICH CLEARS BOTH ARMS' SPREADS. One CPU thread on a
0.39 MMAC int4 matvec is slower than a whole NPU dispatch of it, per call cost
included. The hypothesis is dead.

✅ 2) THE GATE IS KNOWN TO HAVE FIRED, because it says so:
"charsiu: blk.0.inp_gate.weight stays on the CPU -- that call is 393216 MACs,
under CHARSIU_NPU_MIN_MAC=1000000". Round 408's lesson was a refusal nobody
could see; this one whines once, on stderr, naming a tensor and the knob.

✅ 3) AND gemma-3-1b IS A NULL CONTROL THAT CAN BE SHOWN TO BE ONE. Its
smallest dispatch is the q/k/v pair at 1.77 MMAC, above the threshold, so the
gate cannot reach it -- and the refusal line did NOT print for it. A control is
only a control if the thing under test provably could not touch it.

⚠ 4) THE UNIT HAD TO BE THE CALL, NOT THE TENSOR, AND THAT NEARLY BROKE IT.
gemma4's attn_k and attn_v are 256 x 1536 -- the SAME shape as inp_gate, to the
element. A rule keyed on the tensor refuses k and v as well, and those two ride
q's fence for free. Summing the pair keeps them at 3.9 MMAC. The cost is charged
to the call, so the gate belongs on the call.

🔑 5) THE FENCE TABLE HAD ALREADY SAID SO AND I DID NOT READ IT. Broken out by
output width, the narrow buckets -- n 256 (118 calls), 512, 2048, 4096 -- are
ELEVEN of a 339 ms fence. The three wide buckets are 333. gemma4 spends its
token on bytes, not on dispatches, and the instrument printed that before the
board round rather than after.

5. 🏁🏁 THE IOMMU CEILING IS 100%, AND IT NEEDED NO FLASH AT ALL
---------------------------------------------------------------------
r413 §8 said the ceiling on attach-once needed a kernel debug patch and
therefore a reflash. r413 §7 went further and guessed the answer: an IOMMU
domain belongs to an open DRM file, charsiu opens accel0 twice, rocket gives
each file ONE scheduler entity spanning all cores, so "either domain can land
on either core" -- attach-once degenerates into detach plus attach on nearly
every job, and "the 19.5 ms was never merely unmeasured: it was a saving that
was not available."

The premise is right. The conclusion does not follow. §7 stopped at "one entity
spans all cores" without reading how the scheduler picks WITHIN one.

    drm_sched_pick_best takes the FIRST STRICT MINIMUM
      -- sched_main.c:976, `num_score < min_score` -- so a TIE goes to
         sched_list[0], which is core 0.
    rocket_job_push arms AND pushes inside one guard on rdev->sched_lock
      -- rocket_job.c:240, and sched_lock is per DEVICE (rocket_device.h:18),
         not per file -- so two sequential submits from one thread are ordered.
    charsiu submits EVERY device before waiting on any
      -- npudev.c, "ONE JOBLIST PER DEVICE, BOTH ISSUED BEFORE EITHER IS
         WAITED ON".

So: both devices sent, file 0 arms against (0,0) and takes core 0, file 1 arms
against (1,0) and takes core 1. Only device 1 sent, file 1 ties and takes core
0 -- and that is the ONLY case that moves a core's domain.

🔑 11) WHICH IS A QUANTITY charsiu ALREADY HAS. A device with no slices
contributes no megabytes, and account_call is the single point every matvec and
group call passes through. The counter is eleven lines, and it ran tonight on
the shipping path:

    model          calls    both   dev0 only   dev1 only   core 0 flips
    gemma-4-E2B    13572   11332        2240           0      0 (0.00%)
    gemma-3-1b      6724    5060        1664           0      0 (0.00%)
    tinyllama       5700    5700           0           0      0 (0.00%)

⭐⭐ 12) NOT ONE CALL IN 26,000 SENT DEVICE 1 ALONE, and it is structural rather
than lucky: deal_pick breaks its tie to device 0 (`load[0] <= load[1] ? 0 : 1`),
so the first slice of any call always lands there. Core 0 therefore always
carries domain 0, core 1 always carries domain 1, and NEITHER EVER CHANGES.
Every per job attach and detach in the run is removable. The ceiling is 100%.

⚠ 13) THIS IS A MODEL OF THE SCHEDULER, NOT A READING FROM IT, and the line
prints saying so. Two things it cannot see: the both-devices case is a RACE --
if device 0's job retires between the two ioctls, file 1 ties onto core 0 as
well and flips it, so core 0's figure is a LOWER bound -- and it assumes these
two opens are the only entities on these cores. What it settles is r413's claim
that the saving was not available. It is available, on every job.

🔑 14) MEASURING THE GAIN STILL NEEDS A FLASH. The ceiling did not; the A/B
does, and that is the user's call. The patch is drafted and held.

6. ⭐ WHERE gemma4's TOKEN ACTUALLY GOES, AND IT IS THE PER CALL FLOOR
---------------------------------------------------------------------
The decode stage table at the vendor's own prompt length, gemma4 against
gemma3, one boot, performance governor. gemma4's token is 2.30x gemma3's.

    stage              gemma4          gemma3         ratio
    token embedding    1.03 ms  0.9%   0.02 ms  0.0%  51x
    q k v              8.89     8.0    4.27     8.8   2.08
    attention         10.13     9.1    4.27     8.8   2.37
    o proj             7.26     6.5    3.34     6.9   2.17
    gate + up         36.34    32.6   14.64    30.2   2.48
    down              20.91    18.8    9.76    20.1   2.14
    residual           6.42     5.8    0.18     0.4   36x
    output head       16.90    15.2    9.56    19.7   1.77
    TOTAL            111.4           48.5             2.30

Every stage tracks the 2.30x except two, and both are the per layer embedding:
`token embedding` carries per_layer_model_proj and the second table row called
`residual` is where inp_gate, the gelu, proj and the norm are accounted. 7.45 ms
against gemma3's 0.20.

⭐⭐ 15) AND THE 6.42 IS THE PER CALL FLOOR, TO TWO PERCENT, not arithmetic.
70 dispatches a token (35 layers x inp_gate and proj), so 6.42 / 70 = 91.7 us a
dispatch. The fitted cost is 78 us a call + 129.1 us a MB; the pl weights are
1536 x 256 int4 = 0.1875 MB, halved across the two cores, so

    78 + 129.1 x 0.094 = 90 us   against a measured 91.7

🔑 16) WHICH IS WHY §1 LOST AND WHY IT MATTERS. The block is not slow because
the arithmetic is slow; it is 0.39 MMAC and the hardware does it in the noise.
It is 70 ROUND TRIPS, and a round trip is the floor. Moving them to the CPU
(§1) makes the round trip worse. Making the round trip cheaper is the only
lever, and §5 just measured that a full IOMMU detach and attach sits inside
100% of them.

So "fix gemma4" and "the 19.5 ms IOMMU number" are the same item, and gemma4 is
the model where the floor is the largest share of the token. That is the case
for the flash, and the flash is the user's call.

7. ⭐ ONE LINE CARVED OUT OF attach-once, AS ITS OWN Fixes: PATCH
---------------------------------------------------------------------
Reading §5's scheduler path surfaced a correctness bug beside it, in upstream
rocket rather than in ours:

    rocket_job_handle_irq():
        iommu_detach_group(NULL, iommu_group_get(core->dev));

iommu_group_get() returns the group with a kobject_get on it. iommu_detach_group
takes the group mutex, calls __iommu_group_set_core_domain, and returns -- it
consumes nothing. One group reference leaks per retired job, the kobject never
reaches zero, and rocket_core_fini's own iommu_group_put stops releasing it.

The core already holds the group for its whole life (rocket_core_init takes it
into core->iommu_group, rocket_core_fini puts it) and the OTHER TWO call sites
in the same file use that member -- the attach in rocket_job_run and the detach
in rocket_reset. This one is the odd one out.

⚠ 17) THIS IS NOT A NEW FINDING AND SHOULD NOT BE WRITTEN UP AS ONE.
rfc-send-v12/attach-once/0001 has carried the same observation in its commit
message since 2026-09-02, because attach-once deletes the whole per job detach
and takes the leak with it. Tonight rediscovered it from the other end.

🔑 18) CARVING IT OUT IS STILL WORTH DOING. attach-once adds a field to struct
rocket_core, changes the job lifetime, and has to argue about suspend and
reset; a maintainer can reasonably sit on it. This is one line with a Fixes: tag
that stands alone and can go to stable, and sending it first gives the reviewer
of the big one a smaller diff. Held in iommu-group-leak/, based on 68142f986 --
the same base as v13-prep, which is NOT touched.

    Fixes: 0810d5ad88a1 ("accel/rocket: Add job submission IOCTL")

confirmed by fetching that commit: it added all three call sites at once, two
using core->iommu_group and one not.

⛔ 19) IT IS NOT BUILT. core->iommu_group is a struct iommu_group * at
rocket_core.h:51 and is dereferenced identically two lines away, so this is one
expression substituted for an equal one. That is an argument, not a build, and
the holding README says so.
