round 408, 2026-09-13 — the gather runs while the next job does, and what that
                        is worth against the vendor

r407 named the target and measured its ceiling: the gather of the int4
accumulator is the largest line in the prefill, larger than the fence it waits
behind and larger than both of attention's fences together, and the fence is a
SLEEPING ioctl so every core is idle for it. This round moves the work instead
of trying to make it smaller, which is what every previous attempt did.

  board     ROCK 4D, boot 2606ab9f (r400-r407's boot), npu 594 MHz,
            cpu 2016/2208 MHz pinned, governor userspace
  binary    /root/charsiu_run_final, charsiu 91d51b0
  model     Llama-3.2-1B-Instruct-Q4_0.gguf
  vendor    r393's ladder, measured on this board with their runtime and
            their driver. THE TWO CANNOT SHARE A BOOT -- one arm needs

=====================================================================
1. WHAT WAS BUILT
---------------------------------------------------------------------
charsiu_npu_matmul_defer leaves the answer in the device buffer and returns.
The next charsiu_npu_matmul* call flushes it from just after ITS OWN SUBMIT, so
the gather runs while that job is on the hardware. charsiu_npu_flush is the
caller's obligation before anything reads Y.

The two places it is legal are the ones llama.c already marks as sharing an
input: q/k/v and gate/up multiply one RMSNorm output, are adjacent calls, and
neither reads the other's answer.

THREE THINGS THE DEFERRED GATHER TAKES OFF THE POOL RATHER THAN OFF ITS OWN
TENSOR, each a wrong answer that still reads as fluent text:

  - `g->bseen` says which output ranges have been ASSIGNED rather than added
    to, and the call it now runs inside has reset it for its own slices.
  - `g->bout_stride` is wide * m * 4 and is set per call. gate and up share a
    shape, so the first version worked by luck; q and k do not.
  - batch_outbuf keys buffers on (wide, slots), so gate and up land on the SAME
    entry -- exactly the pair this is for. It now skips an entry that owes a
    gather and allocates a second, rather than flushing before the submit that
    was meant to hide it.

=====================================================================
2. IT WORKS, AND THE FENCE IS THE TELL
---------------------------------------------------------------------
852 tokens, three passes an arm, arms alternating, one warm-up discarded:

    CHARSIU_NPU_DEFER_READ=0   TTFT 6955 / 6927 / 6941   fence 1.82 ms a row
    CHARSIU_NPU_DEFER_READ=1   TTFT 6611 / 6626 / 6794   fence 1.32

    the same 24 tokens out of both arms: identical, 8b02145bf030

1) THE FENCE, NOT THE TTFT, IS WHAT SAYS IT RAN. It falls 1.82 -> 1.32
because the job finishes while the CPU is gathering the previous one, so the
wait that follows is already over. A TTFT that moved without the fence moving
would have been noise, and at this board's ~3% spread that matters.

2) AND THE ENTRY SPLIT NOW HAS A NEGATIVE RESIDUAL, which is the overlap
itself: pack 0.81 + submit 0.06 + fence 1.32 + read 2.05 sums to MORE than the
entry, by 0.54 ms a row. The stages are still each measured correctly; they
simply no longer happen one after another.

=====================================================================
3. AND THE OBVIOUS WAY TO WIDEN IT LOSES
---------------------------------------------------------------------
The deferral only pays where the caller has a second independent matmul, which
is about a quarter of the gather. Rows are independent ALWAYS, so splitting one
tensor's chunk in two should give every tensor something to hide behind.

The hardware side was priced first, charsiu_int4 --cost at k=2048 n=8192:
m=78 is 4792 us and m=39 is 2925, so two halves cost 22% more NPU time.

    no split      TTFT 6829 / 6631   pack 0.81   fence 1.33   read 2.05
    ROWSPLIT=8    TTFT 9153 / 9004   pack 1.46   fence 1.13   read 4.35

3) THE FENCE FELL AND EVERYTHING ELSE DOUBLED. The gather more than doubled
for the same total bytes and the pack nearly did, because both carry per CALL
costs that do not scale with m: charsiu_pack_input fills the whole input buffer
with the zero point before writing anything, and the read walks Y once per
slot. Halving the rows doubles the calls and pays each of those twice.

Same shape as the dma_sync note in npufp16.c: a cost charged on the WHOLE
buffer does not halve when the work does. Default off, code kept, measurement
in the comment.

=====================================================================
4. TWO NOTES IN ONE FILE DISAGREED, AND THE BOARD SETTLED IT
---------------------------------------------------------------------
npudev.c says the four-row gather "lost 2.3x to its four write streams". It
also says, three hundred lines earlier, that tools/bench_gather measured that
same form 1.4 to 2.2x FASTER. Both were true of where they were run.

4) AND bench_gather HAD NEVER BEEN RUN ON THE BOARD. It had a host build rule
only, no board log mentions it, and its own header says the host cannot answer
its question -- "the host is aarch64 with caches that dwarf the board's ... the
ratio is the thing to carry". Built for aarch64 and run here at m = 78:

    n=1024  gather 11.41 ms   walk 1.29x   gather4 1.18x
    n=2048  gather 26.65      walk 1.14x   gather4 1.32x
    n=8192  gather 108.35     walk 1.17x   gather4 1.26x

5) AND A REAL BUG NEXT DOOR: the pooled read's grain was `read4 == 2 ? 2 : 1`,
so selecting the FOUR row form gave the pool a grain of 1 and every worker got
a range read_rows4 refuses for not being four aligned. A knob that disabled the
thing it selects, and the 2.3x was measured through it.

6) FIXED, AND IT CHANGED NOTHING: read 2.31/2.46 ms a row against the pair
form's 2.04/2.46 and the row loop's 2.29/2.29. So the standing note is
CONFIRMED rather than overturned, and the microbenchmark still disagrees with
the runtime by 1.26x. The difference between them is the POOL -- one thread
with four write streams against four threads with sixteen -- which is a
sentence bench_gather's header does not contain and now should.

---------------------------------------------------------------------
The projections' entry is now pack 0.81 + submit 0.06 + fence 1.32 + read 2.05,
and the CPU side (2.86) exceeds the NPU side (1.32). So more overlap buys
nothing: the gather itself is the critical path now, and every lever on the
gather is measured and lost (section 4).

              syncs, plan, emit and poison around them. Of that:

7. WITHDRAWN THE SAME NIGHT: IT IS WRONG ON FIVE MODELS OF NINE
---------------------------------------------------------------------
Sections 1, 2 and 5 were written after the 852 token A/B and the ladder, both
of which are Llama-3.2-1B. tests/board_text_all.sh compares the batched path
against the token loop for EVERY model on the card, and it is the check that
stands between "it batches" and "it is right". Run before merging to stable:

    CHARSIU_NPU_DEFER_READ=1    9 models compared, 5 differing
    CHARSIU_NPU_DEFER_READ=0    9 models compared, 0 differing

11) SO THE DEFERRAL IS OFF BY DEFAULT AND SECTION 5's LADDER IS NOT THE
SHIPPED NUMBER. What ships is this morning's ladder: 7016 ms at 852 tokens,
their lead 1.164x, crossover about 250 tokens. Section 5's 6815 and 1.131x
describe an arm that returns wrong text on Qwen2.5, Qwen3, gemma-3 and gemma-4.

12) AND THE SINGLE MODEL CHECK COULD NOT HAVE CAUGHT IT. Llama-3.2-1B is
identical in both arms, hash 8b02145bf030, at 24 generated tokens and at 852
prompt tokens. board_text_all.sh's own header says this: "prefill_control.sh
has only ever been pointed at llama, because the number it exists to explain is
llama's". The model every speed round uses is the model this fault does not
touch.

Two real faults were found and fixed on the way, and neither was the whole
cause:

  - g->pend held a POINTER into g->obuf, which batch_outbuf reallocs when it
    grows -- and the deferral is what MAKES it grow, since it skips an entry
    that still owes a gather. Llama's distinct geometries fit inside the
    initial capacity of 8 and five other models cross it. An index now.
  - the bseen snapshot was restored at g->bseen_n, which is a high water mark
    and can grow between the defer and the flush.

13) THE DIAGNOSTIC THAT NARROWED IT. CHARSIU_NPU_DEFER_READ=2 records the
deferral and then flushes it before returning, so the same record-and-restore
machinery runs at the moment the plain path would have run it:

    =2    9 models compared, 0 differing
    =1    9 models compared, 5 differing

That proves the machinery right and puts the fault in the pool state that
changes BETWEEN the two calls. After it, the field is found by reading the list
of g-> fields the gather touches rather than by guessing at causes.

14) ONE SUCH FIELD, FOUND AND NOT SUFFICIENT: g->bd1, the per ROW activation
scale the int8 read back multiplies by, is one array on the pool sized for one
call, and the next tensor's pack overwrites it. The w4 branch of the same loop
reads a per channel scale off the slot and does not care. Refusing the deferral
for int8 tensors took it to 7 of 9 rather than 0, so that field is really a
hazard and there is at least one more.

15) THE SHAPE OF THE MISTAKE. The mechanism was confirmed by the right
instrument -- the FENCE moved 1.82 to 1.32, which is not something noise does
-- and a correct mechanism was read as a correct change. What the fence
measures is that the overlap HAPPENED, not that the answer survived it.
