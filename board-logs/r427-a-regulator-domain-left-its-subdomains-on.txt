r427: PD_NPU is switched off at probe with NPUTOP, NPU0 and NPU1 still on
========================================================================

2026-11-14, Radxa ROCK 4D, Armbian 26.11.0-trunk userland.

Why: Vladimir Bely reported (issue #4, and on lore in reply to v16 09/16,
2026-11-13) that on a FriendlyElec NanoPi R76S, which does not enable the
NPU, Armbian 7.3.3 (carrying v14) hangs hard about every second boot,
~30 s in, with "vdd_npu_s0: disabling" as the last console line. His
reading: rockchip_pm_add_one_domain() switches PD_NPU off at probe because
it needs a regulator, before its subdomains are added; the subdomains the
bootloader left on are never idled or powered off, genpd records them as
off, and the bus hangs when regulator_late_cleanup() cuts the rail.

The code agrees (pm-domains.c in Ulf's next, line 914:
"if (pd->info->need_regulator) rockchip_pd_power(pd, false);" runs in
add_one_domain(), and rockchip_pm_add_subdomain() adds the children only
after it). PD_NPU is DOMAIN_RK3576 in Ulf's next; v14/v16 9 made it _R.

Board setup, the same for every arm:

  - N.dtb (md5 e020ef4a): the board's own dtb (1201a529, identical to the
    one in Armbian 26.11.1 and to the one the CI build below produced)
    with domain-supply deleted from power-domain@0 (PD_NPU), npu-supply
    deleted from both npu nodes, and npu@27700000, iommu@27702000,
    npu@27708000, iommu@2770a000 set to status = "disabled". This is a
    board that does not enable the NPU. vdd_npu_s0 (RK806 dcdc-reg2) is
    regulator-boot-on without regulator-always-on, as on the R76S.
  - systemd RuntimeWatchdogSec=20s, so a hang resets the board by itself.
  - Each iteration: systemctl reboot (warm), wait until uptime >= 70 s,
    then one line from pb.sh: PMU registers from regmap debugfs of
    27380000.power-management (0x110 idle request, 0x128 idle status,
    0x214 power control of the 0x4 group, 0x230 status), the genpd state
    of npu/nputop/npu0/npu1, the number of boots in the journal, and the
    count of "vdd_npu_s0: disabling" in dmesg.

The oracle is the register state, not the hang: in 0x214, bit 6/7/8 are
the power-off bits of NPUTOP/NPU0/NPU1 (1 = off). A boot is wrong when
those bits are 0 while genpd lists the domains off-0. A hang is a boot
the journal shows without a shutdown, followed by a watchdog reset.

Between R 2 and R 3 the journal has one extra boot, f4ec2292: its
journal ends at 7.7 s (the flush to /var/log/journal), it has no
shutdown, and the next boot starts 67 s after it started. That is a hang
after the last persisted line, ~30 s plus the 20 s watchdog. So arm R:
11 boots, 11 with NPUTOP/NPU0/NPU1 powered and not idled behind an off
PD_NPU, 1 hang.

The register state matches the R76S's (his 0x110 = 0x13e0, 0x214 =
0x3e; ours has bit 0 of 0x110 and bit 9 of 0x214 set as well).

The fix. Mark a need_regulator domain and every domain below it
off_at_probe when it is added, give genpd "off" as their initial state,
and once the subtree is added switch it off children first
(rockchip_pm_power_off_subtree()), then let the provider register. The
same diff is in two trees, both W=1 clean:

  - ulfh/next + the fix: 3f1cfa7fe0c7 (worktree wt-probeoff); in the v17
    branch it is ef861e4b983e, ahead of the patch that makes PD_NPU _R.
  - v7.3.1 + Armbian's three earlier pm-domains patches + rk3576-npu-v14
    + the fix: 331ceca9f624, exported as Armbian's
    rk3576-pmdomain-power-off-npu-subtree-at-probe.patch.

Fix kernel: gahingwoo/build branch rk3576-npu-probeoff-test (armbian
origin/main + that patch file), fork CI run 43511938301, which logs
"274/364: rk3576-pmdomain-power-off-npu-subtree-at-probe (+41/-6)".
7.3.4-edge-rockchip64, vmlinuz md5 37bb1cf4. Its dtb for the 4D is
1201a529, the same file as before.

Two knobs differ between arm R and arm F, not one: the fix, and 7.3.3
(Armbian 26.11.1) vs 7.3.4 (Armbian main). I have not checked what
7.3.3..7.3.4 and the Armbian patch changes in between do to pm-domains.c,
so the arms are not a single-variable pair. The probe-time state R reads
is explained by the code that the fix changes, and F-N reads the state
the fix is written to produce, but this pair alone does not exclude the
other knob.

NPUTOP/NPU0/NPU1 are powered off (0x214 bits 6..8 set) and were idled
first (0x110 bits 1..4 set) on every boot, matching genpd. The boot count
goes up by one per reboot, every boot's journal ends with "Journal
stopped", so no hang in 10. vdd_npu_s0 is still disabled as unused on
every boot, now with nothing left on behind it.

The 16 "Failed to create device link (0x180) with supplier soc" lines
from rockchip-pm-domain are in the stock 7.3.3 boot too (16) and in the
earlier 7.3.4 build (17); they are not from the fix.

What F-N does not show: the R76S. The 4D hung once in 11 stock boots, the
R76S about every second boot; the register state is the same on both, so
the fix removes the condition on the 4D, but a hang count on the 4D
cannot show a rate of 1/11 going to 0 with 10 boots. A run on the R76S
is the real test.
