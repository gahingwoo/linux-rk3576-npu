1. ⛔⛔⛔ 320 HAS THE DEFECT 448 HAD, AND I SHIPPED IT KNOWING THE RULE
---------------------------------------------------------------------
r412's header says it in as many words:

    binary  /root/charsiu_run_win, md5 28c64b1a6a27 (= /opt/charsiu/charsiu_run,
            the r411 shipping binary; nothing was rebuilt for this section)

§2's table -- 252, 302, 352, 452, the table that produced 320 -- ran on that
binary. `charsiu_run_room`, the in place build, first appears in §7, 200 lines
later. So 320 was derived against the ALLOCATING arm.

The in place ladder only makes the NPU arm faster, and only where the arm is
on, so the crossover moves DOWN. 320 is too high by however much the ladder
buys at those lengths, and the arithmetic in §8/§19 of that round puts the
saving at 302 tokens near 62 ms, which would take that row from +2.3% against
a 2.2% spread -- level -- to roughly +5%, which clears.

"If this arm gets faster again, re-measure. Do not scale this number." r412 §10
says a justification of the form "nothing measured says otherwise" names its

🔑 2) WHAT MAKES IT INVISIBLE IS THAT THE TWO HALVES WERE RIGHT SEPARATELY.

2. ⚠⚠ AND THE TASK TERM IS NOT SMALL, IT IS NOT THERE
---------------------------------------------------------------------
The runtime fits `us a call = A + B a task + C a MB` on every staged run and
prints it. Two models, one boot, one binary, this round:

    Qwen3-0.6B      us a call = 68 + -0.1 a task + 118.4 a MB
    (second model)  us a call = 32 + 22.6 a task + 114.7 a MB

⚠ 3) B READS -0.1 AND 22.6. That is not a noisy estimate of one quantity, it
is a coefficient the data cannot determine: tasks and megabytes move together
across the shapes a real model presents, so the fit splits their sum almost
arbitrarily between them. The C term, which IS determined, reads 118.4 and
114.7 against a shipped 110.0 and is fine.

⛔ 4) SO `DEAL_US_TASK 36.8` IS WORSE THAN "FIVE TO TWELVE TIMES TOO LARGE",
which is how it was described last night. It is a number taken from a fit that
never determined it, and it is still steering which core every slice lands on.
The board list already has it. What this round adds is that re-deriving it from
the same kind of fit will not work either: the instrument that would price it
is the one that cannot see it.

⚠ 5) AND THE RUNTIME SAYS SO ITSELF, on the Qwen3 run: "that remainder is
NEGATIVE, so the hardware path and the wall clock are counting different calls
-- the rate above is not a fact about the hardware". The guard fired. Nobody
had read it against the fit on the line below.

=====================================================================
3. 🔑 THE IOMMU NUMBER: BOTH INSTRUMENTS NEED A FLASH, AND THE SAVING
   MAY NOT EXIST TO BE MEASURED
---------------------------------------------------------------------
"About 19.5 ms of a decode token is the per job IOMMU attach and detach" is
the one number in this project's writing that is derived rather than measured:
a per call floor multiplied by a call count. Two ways to settle it were
prepared, and preparing them answered a different question first.

⛔ 6) ftrace CANNOT RUN ON THIS BOARD. The kernel the board boots is snapshotted
in kernel/base.config, and it says

    # CONFIG_FTRACE is not set
    # CONFIG_KPROBES is not set

Everything in kernel/trace/Kconfig is inside `if FTRACE`, so there is no
function_graph tracer; fs/Makefile builds tracefs only under CONFIG_TRACING,
so /sys/kernel/debug/tracing does not exist there at all. There is no kprobe
route either. The symbols are all traceable in principle -- iommu_attach_group
and iommu_detach_group are exported globals with no notrace, and
rocket_job_run has its address taken by .run_job so it cannot be inlined -- and
none of that matters without the tracer.

So the "no patch needed" option does not exist. Getting this number requires a
reflash whichever instrument is chosen, which makes the debug patch the plan
rather than the fallback. It is prepared, off by default behind its own
Kconfig, and each of its five sites is a jump label nop when disarmed.

⭐⭐ 7) AND THE STRONG A/B MAY HAVE NOTHING TO WIN. An IOMMU domain belongs to
an open DRM FILE. charsiu_npu_open_mode calls charsiu_open(NULL) twice --
npudev.c:1561 and :1569 -- and open_any_accel answers both with the same
/dev/accel/accel0. Two files, two domains, and rocket_job_open gives each file
ONE scheduler entity spanning ALL cores, so either domain can land on either
core.

"Keep the domain attached across jobs" then only saves the jobs whose domain
did not change from the previous one. If the scheduler alternates the two
entities on a core, attach-once degenerates into detach plus attach on nearly
every job -- the baseline plus a kref dance, a LOSS.

🔑 8) SO THE CHEAP MEASUREMENT COMES FIRST, AND IT IS A CEILING. The debug
patch now also counts, per core, how often a job arrives carrying a different
domain than the one before it. One pointer compare. That percentage is the
hard ceiling on anything attach-once can remove, and it is readable from the
same run that gives the floor. Near zero and the A/B is not worth two boots,
and the 19.5 ms was never merely unmeasured: it was a saving that was not
available.

⚠ 9) TWO MORE THINGS THE A/B AS DRAFTED GETS WRONG. attach-once/0001 also
fixes a per job iommu_group_get leak, so its two arms differ by more than the
knob under test. And it is two kernels and two boots, against this tree's own
rule about never A/B-ing across boots on a board that drifts 3%. Gating the
fast path on a runtime knob instead makes it one kernel and one boot, which is
what every other board script here does.
