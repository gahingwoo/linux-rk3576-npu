  rc=0 6cf851807fc9, 0 rk_iommu lines

What this shows:

- Five of six forced timeouts recover: the next run has the baseline
  text and no kernel message, after a 2 s wait (3 of 3) and at once
  (2 of 3).
- Arm 6 did NOT recover. The run right after it gives a different text
  with exit code 0 and 3228 rk_iommu lines, on both IOMMUs (27702000 and
  2770a000), with no job timeout. The run 2 s later ([end]), after npu0
  had gone off, is wrong the same way. A driver reload (rmmod, modprobe)
  brings it back.
- So in this case the bad state outlived a power-off of the core's
  domain, which points at state the driver or the IOMMU driver keeps,
  not only at the hardware. Not established: which state, how often
  (1 of 3 back-to-back arms here), and whether v17 or mainline rocket
  behave the same (not run on this kernel).
- No SoC hang, no SError in any arm.

Not run this round: the NPU-disabled boot (N.dtb, pmdomain 1/3 at
probe); it needs a dtb change and a reboot.

Second part: the timeout that does not recover, found and fixed (test patch)
------------------------------------------------------------------------------

Reproduced with log_buf_len=16M and rep.sh: up to N back-to-back forced
timeouts, stop at the first one the next run does not recover from,
then look at the state.

  run 1: [arm1] ok, [arm2] next at once: b53886cf1677, 7938 rk_iommu lines
         [+3s] npu1=on npu0=off-0;  [+13s] npu1=on, run still wrong
         after unbind/bind of both cores: 6cf851807fc9 (recovered)
  run 2: arms 1-9 ok, [arm10] fails; npu0=on npu1=off-0
         every device of the stuck domain runtime-suspended, the domain on
  run 3: [arm2] fails; npu1 on; PMU 0x214=0x2be (NPU1 power bit 0 = on),
         0x110=0x13e3. Forcing a resume/suspend of both cores
         (power/control on, auto) did not turn the domain off.
         genpd idle_states: Rejected 0 for every NPU domain. No
         "failed to set idle" or "failed to get ack" message.

Reading of it, from the code (drivers/iommu/rockchip-iommu.c, rc4):

  1. After the core reset of a timeout, bank 0 of that core's IOMMU keeps
     paging while bank 1 is back in reset state.
  2. rk_iommu_is_paging_enabled() and rk_iommu_is_stall_active() are true
     only when every bank agrees, so rk_iommu_enable_stall(),
     rk_iommu_disable_paging() and rk_iommu_disable_stall() all do
     nothing for this IOMMU. The force reset then fails its DTE_ADDR
     check on bank 0: "MMU_DTE_ADDR is not functioning", and
     rk_iommu_enable() fails.
  3. That happens in rk_iommu_resume(), while the core, its consumer, is
     RPM_RESUMING. genpd's power-off on the failed resume sees two
     devices not suspended and keeps the domain on; the core's resume
     fails too, both end up "suspended", and nothing tries again. The
     domain never goes off, so the hardware is never reset, and every
     later job fails pm_runtime_resume_and_get() in rocket_job_run()
     without reaching the hardware. Userspace gets the old buffer
     contents and no error.

Test patch (r429/iommufix, not sent): in rk_iommu_enable(), when the
banks disagree on paging, stall the banks that still page, disable
their paging and release the stall, one bank at a time, before the
normal sequence; and print each bank's STATUS and DTE_ADDR when the
DTE_ADDR check fails. Kernel: fork CI run 45145164030 (v18 image
kernel + this patch), vmlinuz md5 74f785d6.

Third part: the patch as it will be sent, and the reboot that did not come back
--------------------------------------------------------------------------------

The board came back after a power cycle by hand. The journal (persistent)
has no entry for the boot that did not come back: the previous boot
(a70f0e00, N-3) logs into its shutdown (armbian-ramlog sync, journal
flush) and the next entry is the power-cycled boot. So it stopped
before journald, in the last part of the shutdown or early in the next
boot; without a serial console on the 4D, where is not known.
