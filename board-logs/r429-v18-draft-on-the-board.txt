r429: the v18 draft on the board, and a timeout it does not recover from
=========================================================================

2026-11-23, Radxa ROCK 4D. A new card: the SD card was rewritten with an
Armbian image built by fork CI for this round, and the SPI flash, which
held EDK2, was rewritten with U-Boot.

Why: v18 (rfc-send-v18) rewrites the clock/reset patch (4/8), moves
GET_PARAM ahead of the RK3576 patch (5/8) and rewrites the RK3576 patch
(6/8). None of that had run on a board.

Arm T: forced job timeouts
--------------------------

rocket.ko rebuilt from rc4 + Lausen + v18 (git am -3, the same 13
commits as the image) against the board's own linux-headers package,
with one test-only module parameter, never part of a patch:
test_timeout_ms, which rocket_job_run() writes into core->sched.timeout
(0 = the normal 500 ms). md5 ffd79346, vermagic matches. t429.sh:
rmmod, insmod the test module, two baseline runs (-n 16), then six
arms. Each arm sets test_timeout_ms=1, runs once (forced), sets it back
to 0, and runs once more: arms 1-3 after a 2 s wait (as in r428),
arms 4-6 at once. Kernel messages counted between markers.

  t = "NPU job timed out", mmu = rk_iommu "Error during raw reset.
  MMU_DTE_ADDR is not functioning", serr = SError or "Internal error".

Then rmmod, modprobe of the normal rocket.ko, and one more run:

  rc=0 6cf851807fc9, 0 rk_iommu lines

What this shows:

- Five of six forced timeouts recover: the next run has the baseline
  text and no kernel message, after a 2 s wait (3 of 3) and at once
  (2 of 3).
- Arm 6 did NOT recover. The run right after it gives a different text
  with exit code 0 and 3228 rk_iommu lines, on both IOMMUs (27702000 and
  2770a000), with no job timeout. The run 2 s later ([end]), after npu0
  had gone off, is wrong the same way. A driver reload (rmmod, modprobe)
  brings it back.
- So in this case the bad state outlived a power-off of the core's
  domain, which points at state the driver or the IOMMU driver keeps,
  not only at the hardware. Not established: which state, how often
  (1 of 3 back-to-back arms here), and whether v17 or mainline rocket
  behave the same (not run on this kernel).
- No SoC hang, no SError in any arm.

Not run this round: the NPU-disabled boot (N.dtb, pmdomain 1/3 at
probe); it needs a dtb change and a reboot.
