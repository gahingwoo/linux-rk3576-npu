                        probes that had never been run

=====================================================================
1. FOUR WAYS TO PUT TWO JOBS ON THE HARDWARE, AND THE ONE THAT SHIPS IS RIGHT
---------------------------------------------------------------------
npu_job_cost has carried this since it was written:

    charsiu opens the accel node twice and submits one job per fd in a `for`
    loop, so the second core starts a whole syscall after the first. But
    charsiu_submit_jobs already takes a LIST [...] If B beats D, the second
    core has been starting late for the life of this runtime.

  A  one job, one ioctl
  B  two jobs, ONE ioctl, one fd      the arm nobody had run
  C  two jobs, two ioctls, one fd
  D  two jobs, two ioctls, two fds    what charsiu does

All four submit everything before waiting on anything, so all four measure the
wall time for two dispatches to finish. 200 repetitions an arm, the four arms
back to back in one process so any drift is common to all of them.

    k      n        A        B        C        D
    1024   256   49.77    95.05    94.74    52.43
    1024   1024 133.64   263.05   263.30   135.66
    2048   2048 489.63   943.00   937.84   471.88

B IS NEVER FASTER. B and C are both twice A and D is equal to it, at every
shape where the arms separate. One fd serialises two jobs whatever the ioctl
count; two fds run them side by side and the pair costs what one job costs.

So the hypothesis is refuted and the runtime is already doing the thing the
comment suspected it of getting wrong. The second fd is not overhead that a
job list would remove. It is the only thing that reaches the second core.

This tree already knew half of it -- "two jobs on the same fd serialise" is
recorded in the narrow-output note from 09-08 -- and the probe's own header was
written without it.

2. AND THE FIRST READING OF THOSE ARMS SAID THE OPPOSITE
---------------------------------------------------------------------
The arms ship at k=64 n=32, where "the arithmetic is nothing and this is
dispatch". The first run of the round read:

    A  20.83    B  44.98    C  74.58    D  112.44 us

which is B beating D by 2.5x -- the answer the header was hoping for, and the
one I was about to write down. It is noise. Three more passes of the same
binary on the same boot:

    k=64 n=32     A       B       C       D
    pass 1     84.21   85.37  131.90   34.02
    pass 2     17.30   26.10   27.09   25.81
    pass 3     71.41  138.77  125.70   42.03

A alone covers 17.30 to 84.21, a factor of 4.9, which is larger than any
difference between arms. THE ARMS ARE NOT ORDERABLE AT THAT SHAPE. The first
run's D was 112.44 and pass 2's was 25.81, from one binary on one boot.

A margin has to clear the arm's own spread, and at 64 x 32 there is no margin
that can. What separates them is a shape whose compute is measurable, and
section 1 is that shape.

3. WHAT CACHE MAINTENANCE COSTS, WITH NO JOB IN THE WAY
---------------------------------------------------------------------
npu_prep_cost preps a buffer that was never submitted, so there is no fence to
wait on and the number is the invalidate alone. 2000 repetitions a row.

       bytes     prep us     fini us     prep GB/s     fini GB/s
        4096        1.41        1.15          2.91          3.56
       32768        3.35        3.11          9.80         10.54
      262144       19.55       19.33         13.41         13.56
     1048576       75.89       75.55         13.82         13.88
     4194304      303.92      303.57         13.80         13.82

AN IOCTL WITH NO WORK COSTS 1.4 US, and the slope saturates at 13.8 GB/s in
both directions. The old decode decomposition put "about 5 us of syscalls" in
the per-call floor; a prep and a fini together at the smallest size are 2.6.

WHAT IT SAYS ABOUT THE OUTPUT BUFFER. charsiu's decode output is
`(slots + 1) * out_stride + 4096` per device and out_stride is
CHARSIU_NPU_NMAX * 4, which is 32 KB whatever the tensor's own n is. The tool
was written to ask whether sizing that to the tensor is worth doing, with its
own criterion: worth it if the invalidate is a meaningful part of the 114 us a
call, not worth it if it is 2 us.

It is neither. One slot is 68 KB and costs about 5.6 us of prep and 5.5 of
fini; four slots are 164 KB and cost about 13 and 13. So it is 10 to 26 us a
call depending on how many slices the deal gave that device -- 9 to 23% of the
call. THE ANSWER DEPENDS ON THE SLICE COUNT AND THE TOOL COULD NOT HAVE KNOWN
THAT, because the buffer is charged whole and the tool priced bytes.

That is a lead and not a result. Nothing here measured a decode with a
narrower stride, and out_stride is read by the job's output address and by the
readback, so making it per tensor is a change to the read path. It is written
down rather than done.

4. WHAT ONE DISPATCH COSTS BY OUTPUT WIDTH, CONTROLLED
---------------------------------------------------------------------
npu_fence_scan holds k, m and the buffers still and moves only n. Buffers are
allocated once at the widest point, so no row pays for an allocation -- this
tree has measured an allocation and called it a matmul before. k=1024, m=80,
int8, 20 repeats a point.

       n   submit us    fence us   fence us per n
     256         6.3       376.5         1.4709
     512         5.6       367.7         0.7181
    1024         5.9       551.3         0.5384
    2048         7.4       664.2         0.3243
    4096         8.5      1094.0         0.2671
    8192         9.2      1917.2         0.2340

THE LAST COLUMN FALLS, SO THERE IS A FIXED COST. Two points at the wide end
give fence = 246 us + 0.204 us per output channel, and that line predicts
n=4096 to within 1%. The submit is 6 to 9 us and does not grow with n.

AND IT CORRECTS A NUMBER ALREADY IN THE TREE. Bucketing the fence by tensor
width inside a real forward pass gave "about 1.3e-4 ms per output channel",
which is 0.13 us, with no fixed term. That fit had nowhere to put the 246 us,
so it spread it across the slope and came out 36% low. The bucketed version
mixes tensors with different slice counts and charges a device a whole fence
even on calls where the deal gave it no slot; this one does not.

Two points still only fit a line. What is quotable here is the two raw
readings and the fact that the per-channel column falls, not the coefficients.

5. CHAINING TASKS INSIDE ONE JOB BUYS NOTHING, AT A REAL SHAPE
---------------------------------------------------------------------
The same probe prices tasks chained in one job. At the shipped 64 x 32:

        tasks     us a job      us a task
            1        70.06          70.06
            4        67.49          16.87
           16       222.76          13.92

which reads as a 4x amortisation and would make packing several tensors into
one job the lever. At k=1024 n=1024, two passes:

        tasks   pass 1 us a task   pass 2 us a task
            1            142.59            137.51
            4            155.57            131.39
           16            161.32            124.01

FLAT, AND THE TWO PASSES DISAGREE ABOUT THE SIGN. There is nothing to
amortise: at m=1 a dispatch costs what its weights cost to read. The byte
sweep in the same tool gives 128.9 us for the 1.05 MB this shape reads, and
the one-task row is 137. Chaining sixteen tasks reads the weights sixteen
times, and that is the whole bill.

The 64 x 32 table is the fixed cost with no work to hide it, measured in the
region section 2 shows cannot order anything.

7. ONE WIDTH LAW INSTEAD OF FOUR
---------------------------------------------------------------------
The accumulator surface can only name an even batch width, because P = m / 2
in charsiu_acc_index covers 64 * P slots per group where the group needs
32 * m. That rule was written out four times -- the gate in npudev.c as
`(m % 2) == 0`, the chunker in charsiu_run.c as `w &= ~1`, acc_index_check as
`m % 2 == 0` again, and the map itself -- and the sweep compared the map
against its own copy. The two decisions that reach the hardware were watched
by nothing.

charsiu_acc_width_ok now lives beside the map and all three call it. The
chunker's rounding is unchanged on all of 0..100000 and the host perplexity is
identical before and after.

8. THE BOARD WENT DOWN TWICE, BOTH TIMES UNDER version_all.sh
---------------------------------------------------------------------
r418's silence and one in this round both happened while that script was
asking the installed binaries for their commits. It is not established as a
cause: a mains cut took the board out once this week as well, and nothing
survives the death to say which binary was running, because the script prints
only AFTER a binary returns and the output goes down an ssh pipe that dies
with it.

There is a mechanism on the shelf. npu_job_cost's own source records that a
job submitted past the device's limits "timed out, and took the IOMMU with it
-- MMU_DTE_ADDR is not functioning [...] and the board was dead for five
hours". version_all's header records that a tool which does not recognise
--version sends argv[1] through atoi, "and an unrecognised --version becomes a
dimension of ZERO submitted to the hardware". Seven of the binaries did
exactly that in r418.

The script now writes each binary's name to $DIR/version_all.last and syncs
before starting it, and writes "finished cleanly" at the end so a stale line
cannot be read as the killer. Both directions watched on the desk. The next
time the board goes down under it, the file names the binary.

9. A DISPATCH AT m=1 IS A WEIGHT READ, AND int4 IS EXACTLY HALF OF int8
---------------------------------------------------------------------
npu_fence_scan takes k, m and a dtype, so the surface can be walked rather
than fitted at one point. Least squares on all eight n of each row, m=1,
20 repeats a point, buffers allocated once.

    k      int8 us/n    int4 us/n    ratio    int8 GB/s    int4 GB/s
    1024     0.1167       0.0595     0.51        8.83         8.32
    2048     0.2300       0.1168     0.51        8.94         8.84
    4096     0.4370       0.2224     0.51        9.40         9.24

THE SLOPE DOUBLES WHEN k DOUBLES, over a 16x range of k: int8 goes 0.0328,
0.0618, 0.1167, 0.2300, 0.4370 for k of 256 to 4096, which is x1.89, x1.89,
x1.97, x1.90. So the cost is the weight BYTES, k * n of them for int8 and half
that for int4, and the rate is 8.3 to 9.4 GB/s either way.

AND THE HALVING WAS AN INFERENCE UNTIL NOW. The tool's own header says every
earlier sweep dispatched int8 and the cost model was "carried to a w4a16
prefill by halving the weight bytes on paper". Measured, the ratio is 0.51,
0.51, 0.51. The paper halving was right and it is no longer an assumption.

WHAT THAT RATE IS. charsiu_membw on the same boot gives one CPU core 8.63
GB/s of DRAM. A single NPU dispatch at m=1 reads its weights at 8.3 to 9.4.
The two agree to within the spread, so a decode dispatch is at the
single-stream memory roof for its weights, and what is left to win at m=1 is
BYTES rather than calls.

THE INTERCEPT IS NOT DETERMINED AND IS NOT QUOTED. The fits put it between 13
and 104 us and the same k measured twice in this round gave 71.4 and 52.0. The
line describes the wide end to 6.5% at k=4096 and 31% at k=256, which is a fit
that describes without determining its constant. Two points always fit a line
and eight points fit this one only where n is large.

10. AND WHY PREFILL BATCHES, IN ONE SURFACE
---------------------------------------------------------------------
The same scan at k=1024 int8 with m moving:

    m       us per n at the wide end
     1        0.111
     8        0.118
    20        0.122
    40        0.131
    80        0.202

EIGHTY TIMES THE ROWS FOR 1.8 TIMES THE COST. The weights are read once for
the whole batch, so everything above m=1 is nearly free per row: 0.0025 us a
channel a row at m=80 against 0.111 at m=1, a factor of 44.

That is the same fact as "prefill batches and decode cannot", measured as one
surface instead of inferred from two separate rounds. It also says where the
batched path stops paying: the slope is flat from m=1 to m=40 and then jumps
by half at m=80, so the widest chunk is not free.

11. A VARIABLE SPELT WITH A CYRILLIC LETTER, AND A CLEANUP THAT ATE A TEST
---------------------------------------------------------------------
Sweeping the tree for glyphs turned up two things that are not decoration.

src/npuquant.c's w4clip search declared `double beste = -1.0` with a CYRILLIC
SMALL LETTER IE where the final e should be, and used the same spelling in all
three uses. It built, it ran, and it was correct. What it was not was
findable: `grep beste` returns nothing, `grep best` shows a name that looks
ASCII, and retyping it gives a different identifier. It sits beside `bestd`.

tools/check_ascii.py is the rule made to run. A non-ASCII character inside a
comment or a string is usually DATA that has to stay -- tokenizer.c explains
SentencePiece's U+2581 and cannot do it in ASCII, npuquant.c quotes a model's
own garbled output -- so the rule is not "no non-ASCII in the file", it is
"none in the CODE", which needs the comments and strings parsed rather than
grepped around. Eight self-test cases including an escaped quote followed by
code and a comment opener inside a string. In `make test`, 72 files clean.

AND THE SECOND ONE IS MINE. Commit 5051745, "strip every emoji from the tree",
took a U+2713 and a U+1F642 out of tokenizer_roundtrip's unicode case. Those
were not decoration: they were the three and four byte UTF-8 the round trip
existed to cover. What was left said "unicode: <CJK> <accented> emoji " -- a
test input naming a case it had stopped testing, which is this project's
oldest fault wearing a new hat and I wrote it while enforcing a rule.

Restored as hex escapes so the source stays ASCII and the bytes are unchanged:
11 tokens to 14, round trips.

THE REST OF THAT COMMIT IS CLEAN AND THAT WAS CHECKED RATHER THAN ASSUMED. All
257 other non-ASCII removals in its code files are warning prefixes on messages
whose text did not change. It touched no md5, no corpus bytes, and
corpus_fixed.sh still reports 0 of 4 files changed.

12. THE RUNTIME'S OWN COUNTERS AGREE WITH SECTION 9
---------------------------------------------------------------------
A decode with CHARSIU_STAGES on Llama-3.2-1B, same boot, prints its own fit:

    us a call = 24 + 22.2 a task + 116.1 a MB (both on the busier core), so of
    2652 ms in the hardware path 98 ms is per call, 251 ms is per task and
    2303 ms is the weights at 17.44 GB/s across 2 cores
    13% of the DECODE hardware path is dispatch rather than bytes

116.1 us a MB is 8.6 GB/s on one core. Section 9's controlled sweep, with the

drops stderr gets a decode with no accounting and no indication that there was
any to have.

13. THE OUTPUT SLOT STRIDE FITS THE TENSOR NOW, AND IT IS 2 TO 3%
---------------------------------------------------------------------
Section 3 left this as a lead: the output buffer is (slots + 1) * out_stride
and out_stride is nmax * 4, which is 32 KB whatever the tensor's own n is,
while charsiu_bo_prep invalidates a WHOLE buffer object. What section 3 could
not say is how much that costs, because the answer depends on how many slices
the deal gave each device and nobody had counted.

  board     ROCK 4D, boot 1b50bcda, 594 MHz, boot entry 1, performance
            governor. THIS IS A DIFFERENT BOOT FROM SECTIONS 1 TO 12: the
            board restarted between them, so nothing here is compared with a
            number from boot 8934c5ee.

Two counters now print it. Over 32 tokens:

    model            charged   written   ratio
    Llama-3.2-1B     289.0 MB   78.1 MB   3.7
    gemma-3-1b       273.6      55.4      4.9
    Qwen3-0.6B       301.9      38.4      7.9
    Phi-3.5-mini     535.5     151.1      3.5

QWEN3 PAYS EIGHT TIMES WHAT IT WRITES, which is what a model of narrow tensors
does against a stride sized for the widest.

AND THERE IS NO CHEAP FIX AT THE IOCTL. DRM_ROCKET_PREP_BO is a handle, a
reserved word and a timeout: no offset, no length. The kernel cannot be told
about a range, so the only way to invalidate fewer bytes is to have fewer
bytes. Each entry now takes a stride of its own widest slice, which is the
same change the buffer SIZE makes -- on Llama the charge falls from 559.5 MB
to 207.2 MB for the same 150.6 MB written.

One binary, arms alternating, three readings each, 128 generated tokens:

    model            FIT=0 (range)     FIT=1 (range)     margin
    Llama-3.2-1B     21.18 (0.38%)     21.60 (0.19%)     +1.98%
    Qwen3-0.6B       26.21 (1.68%)     27.04 (0.55%)     +3.17%
    gemma-3-1b       20.21 (0.00%)     20.62 (0.34%)     +2.03%
    tinyllama-1.1b   22.03 (1.70%)     22.54 (0.27%)     +2.29%

EVERY MARGIN CLEARS BOTH ARMS' OWN SPREAD, and the text is identical on all
ten models the board holds, which is the bar board_text_all.sh sets. It is the
default now and CHARSIU_NPU_OUT_FIT=0 puts the old stride back.

THE THIRD PLACE WAS THE ONE WORTH FINDING. A stride appears at the address
every slot writes to, at the address the read back walks, and at a BOUNDS
CHECK between them that asks whether the last slot fits in the buffer. The
first two are where a wrong stride is a wrong answer; the third is where a
right stride looks like a wrong one, because a correctly fitted buffer is
smaller and the check compared it against the old width. All three move
together.

AND THE BYTES DO NOT EXPLAIN THE GAIN. 352 MB at npu_prep_cost's 13.8 GB/s is
25 ms of a 6042 ms run, 0.42%, against a measured 1.98%. Something besides the
cache maintenance moved: a smaller buffer is also fewer pages to allocate and
map, and this tree has measured an allocation and called it a matmul before.
That is an open attribution and the knob is what closes it.

WHAT WAS CHECKED AND FOUND ALREADY DONE. The activation buffer's PREP is off
by default since round 367, because the device only reads it. Its FINI is not
optional -- the CPU wrote those bytes and the clean is what makes them visible
-- and DRM_ROCKET_FINI_BO has no range either, so a counter prints what it is
charged on rather than leaving it to be inferred.

THE FIRST ATTEMPT DIED AND THE SECOND ONE CAUGHT A LIVE HOLE. Two things,
both worth keeping.

A LOCAL `nohup ssh board '...' &` DOES NOT DETACH THE REMOTE JOB. The local
wrapper was reaped, the ssh went with it, the board-side sh took SIGHUP, and
the board came back at load 0.00 with no process. The half-written file looked
exactly like a run still going, because section 2's grep was block-buffered and
had printed only its heading. `pgrep -fa ssh` then matched its own command line
and said it was still running. The fix is to detach ON THE BOARD --
`setsid nohup sh -c "... > /root/out 2>&1" </dev/null &` -- and poll that file
over separate short ssh calls.

AND THE PIPE THAT MADE HOLE ONE INVISIBLE WAS STILL THERE. r414 wrote
board_regress.sh because the board copy called arch_sanity with no argument and
printed a usage line under a green heading. That fix supplied the argument and
left `| tail -16` in place -- and the pipe is what made the bug invisible, not
the missing argument: a pipeline's status is its last command's, tail always
succeeds, and `set -e` sees nothing.

Every section goes through a `run` helper now that checks the real status. On
its first board run it stopped at section 2 with
"FAILED: ... board_text_all.sh: No such file or directory". That script IS in
the installer's PROBE_SCRIPTS list and probe_list.sh passes: the list was right
and the board was older than the list, which is r418's finding for the probe
binaries repeated for the scripts. Under the old harness that failure would
have gone through `| grep -E "gguf|models compared"`, printed nothing, and the
run would have continued with section 2 green over a check that never ran.

The harness now preflights every script, binary and model before section 1. One
second, against twenty minutes to find it last.

AND "COMMENT ONLY" NEEDED PROVING. dev had one commit touching src/ after the
regressed binary, nine lines of comment. Pinning the stamp through CFLAGS does
not pin it -- the Makefile's `override CFLAGS +=` appends its git describe value
AFTER the caller's, the two builds differed by a dirty-tree suffix in .rodata,
every address after it shifted, and .text differed too. Pinned properly with
`make CHARSIU_BUILD=fixed` the two builds are the same md5.
