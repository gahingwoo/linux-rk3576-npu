round 391, 2026-09-12 — what the CPU clock is worth, the half r390 did not touch

r390 swept the NPU clock and closed with its own warning: the vendor's
published figures are "at the maximum CPU *and* NPU frequencies", only the NPU
half was varied, and a decode that ignores the NPU clock is a decode that may
well be bound by the CPU. This is that measurement.

🔑 UNLIKE THE NPU CLOCK, THIS ONE MOVES WITHIN ONE BOOT. The NPU rate lives in
the device tree, so r390 spent a reboot per arm and had to measure the
boot-to-boot drift it was warned about. cpufreq is sysfs. Every point below is
the same boot, the same load, the same binary, swept up and then back down.

⚠ THE FREQUENCY IS CONFIRMED, NOT ASSUMED. scaling_setspeed is a request and
scaling_cur_freq is what happened; every block printed both and every block
got what it asked for. This kernel exposes no thermal zone, so the up-then-down
sweep is the only throttling detector there is.

⚠⚠ THE CPU-ONLY ARM IS A POSITIVE CONTROL AND IT IS NOT DECORATION. If a
measured arm comes back flat, "the CPU clock does not matter here" and "my knob
never took effect" are the same reading. SmolLM2-135M with CHARSIU_NPU=0, same
harness, same parser, MUST move. It moved 2.49x.

CONDITIONS  two boots. Vendor on the vendor786 arm (RKNPU bound, NPU 786.432
            MHz, boot 515b234c); charsiu on npu594 (rocket bound, both cores,
            NPU 594 MHz, boot 831b92ba). Rail 800 mV in both. Vendor figures
            from their own RKLLMPerfStat via vendor_bench; charsiu from
            charsiu_run dated 2026-09-12. 3 repeats a point, one warm-up
            discarded, swept up and back down.

⚠⚠ THE TWO RUNTIMES ARE AT DIFFERENT NPU CLOCKS HERE, SO NO ABSOLUTE
CROSS-RUNTIME NUMBER BELOW IS A LIKE-FOR-LIKE COMPARISON. What is compared
across them is each one's ELASTICITY -- how its own numbers move when its own
CPU clock moves -- which is measured inside one boot and one arm.

🏁 1) THEIR DECODE RIDES THE CPU. r390 found the NPU clock worth -0.9% to
them; the CPU clock is worth +21.8%. Whatever bounds their decode, it is much
closer to the CPU than to the NPU.

🏁 2) AND SO DOES OURS, BY THE SAME FACTOR. x1.2188 against x1.2177 -- the same
number to three digits, from two different boots and two different runtimes.

🏁 3) SO THE DECODE RATIO IS FLAT IN CPU FREQUENCY. 1.392, 1.410, 1.393 across
a clock that more than doubles. That is the opposite of r390, where the NPU
clock moved the ratio 1.389 -> 1.461. ⭐ The fairness worry about section 1 is
answered for decode: running at their published maximum moves both columns by
the same proportion and leaves the ratio where it was.

   charsiu's repeats agree to 0.06-0.2%; theirs to 2.6-2.9%, with BOTH
   endpoints reading faster on the second visit. Not throttling. Unexplained.

🏁 4) THEIR PREFILL RATE DOES NOT USE THE CPU AT ALL AND THEIR FIXED COST IS
MADE OF IT. Per token the two conditions are the same number to within 1.4%;
the whole TTFT improvement is the intercept, and it HALVES. With r390's 6.5%
for the NPU clock: their rate is the NPU's, their fixed cost is the CPU's.

🏁 5) OURS SPLITS THE OTHER WAY, AND THE FIXED COSTS CROSS OVER. Our rate does
move with the CPU (-7.0%) and our fixed cost moves much less than theirs
(-23.9% against -51.9%). At schedutil our fixed cost is 16% BELOW theirs
(143.3 against 171.0); at max CPU it is 33% ABOVE (109.0 against 82.2).
⭐ Which runtime starts a prompt faster depends on the governor, and every
round this tree has run picked the governor that flatters us.

⚠ A one-prompt TTFT comparison cannot see any of this. Two lengths cost one
extra run per condition and turn one uninterpretable number into two.

=====================================================================
⛔ AND THE FIRST CHARSIU SWEEP OF THIS ROUND WAS THROWN AWAY
---------------------------------------------------------------------
It read 13.85 tok/s at max CPU where r388 recorded 17.85 at a LOWER clock,
which is impossible, so it was not published -- it was reproduced on the same
boot against the alternative and the difference was found. The script had
copied clock_cost.sh's three environment knobs. The tree's board environment
has five, and the missing one was CHARSIU_NPU_MAXN.

Its C default is 8192. The model's output head is 128256 rows wide. Under 8192
that head silently stays on the CPU, and it is worth 55% of decode
(13.89 -> 21.50 at max CPU, same boot, same binary, one variable).

⚠⚠ THIS IS THE SAME BUG AS CHARSIU_COEF_ELEMS, ONE KNOB OVER. job.c already
carries the argument in full -- only charsiu-runner and charsiu-serve set the
variable, every board test sets it too, therefore the C default was never what
anything measured -- and that argument was acted on for COEF_ELEMS and not for
MAXN, which sits three lines away in llama.c with the same two setters and the
same board tests. Fixing the instance instead of the class.

---------------------------------------------------------------------
THE DEFAULT WAS CHANGED, AND VERIFIED ACROSS THE ZOO

262144 is now the default at both sites. The card carried three models when
that was written; seven more were copied over the network, byte sizes checked
against the desk, and board_text_all.sh run over all of them with the new
binary and NO environment set -- so every row below is the bare default doing
what only the wrappers used to do:

  Phi-3.5-mini   Qwen2.5-1.5B   Qwen3-0.6B   SmolLM2-1.7B   SmolLM2-135M
  gemma-3-1b     gemma-4-E2B    tinyllama-1.1b   Llama-3.2-1B

  9 models compared, 0 differing, every one "prompt batched, text identical"

Every row says `prompt batched`, not `prompt a token`, so the batched path was
actually exercised on each. Text is also byte-identical between MAXN=8192,
MAXN=262144 and the bare default on the three models checked directly.
