round 389, 2026-09-12 — the vendor's LLM runtime, RUN, on this board

Every speed comparison this project has published against Rockchip used the
figures in their benchmark.md: a point estimate at maximum frequency, with no
N and no spread, from a runtime nobody here had ever run. docs/paper-evidence.md
says so in its "what is not supported" section. This round removes that.

WHAT MADE IT POSSIBLE, and none of it was new work today:
  - Kiln's mainline port of the vendor rknpu driver. Built against the board's
    own kernel in one command; its shims carried from 6.1 to 7.2-next without
    an edit. vermagic matched exactly.
  - the Kbuild note that librkllmrt discovers the NPU through the DRM render
    node, which is why the DRM_GEM path is the one to build.
  - the vendor node from Kiln's 7.1.3 tree, already in mainline naming.
  - Llama-3.2-1B-Instruct-rk3576-w4a16.rkllm, md5 2d3962468e2e7c0d0571157f8c9eae71
    -- the SAME file the quality comparison scores.

CONDITIONS, held equal except where noted:
  kernel    7.2.0-rc5-next-20260730+ #10, the same Image in both arms
  clock     594 MHz in both
  cpu       both runtimes pin the big cluster; the vendor prints
            "Enabled cpus: [4, 5, 6, 7]", charsiu does it in a58086c
  model     Llama-3.2-1B, w4a16 for the vendor and Q4_0 for charsiu
  prompt    identical strings, -n 16, ignore-eos, context 512
  ⚠ rail    charsiu 800 mV, vendor 750 mV. The vendor driver sets the rail
            through npu-supply and its OPP table and does not take the device
            tree's 800 mV floor. Both arms compute correctly at 594 MHz, and
            voltage does not set clock rate, so this is a caveat rather than a
            confound -- but it is not nothing and it is stated.

=====================================================================
1) DECODE
=====================================================================

  charsiu  18.56 tok/s   (18.47..18.58, five runs)
  vendor   12.88 tok/s   (12.71..12.95, four runs)

🏁 charsiu is 1.44x the vendor's decode, measured against their runtime rather
than against their published figure.

=====================================================================
2) PREFILL, and the single-prompt answer is a trap
=====================================================================

⚠⚠ THE TWO RUNTIMES DO NOT TOKENISE THE SAME STRING THE SAME WAY. The vendor
wraps the prompt in its own chat template and reports 50 tokens where charsiu
reports 16. One prompt therefore measures an unknown mixture of "how fast is
the prefill" and "how much prefill is there", and the two readings of it point
in OPPOSITE directions:

  wall-clock TTFT, same string   charsiu 265 ms      vendor 466 ms
                                 charsiu FASTER, 1.76x
  prefill throughput             charsiu 61 tok/s    vendor 107 tok/s
                                 vendor FASTER, 1.76x

Both are true and neither is the answer. Two prompts separate them. A second,
longer prompt: 79 tokens for charsiu, 113 for the vendor.

                 short            long            ms/token   fixed
  charsiu     16 tok  265 ms    79 tok  751 ms      7.71      141.6 ms
  vendor      50 tok  466 ms   113 tok  860 ms      6.25      153.6 ms

🔑 THE SLOPE IS THE RATE AND THE INTERCEPT IS THE OVERHEAD.

  - per prompt token the vendor is 1.23x faster, 6.25 ms against 7.71. That is
    the real prefill gap and it is much smaller than any single-prompt reading
    suggests.
  - the fixed cost is nearly the same, 142 ms against 154, and charsiu's is
    slightly LOWER.
  - charsiu's wall-clock win on a short prompt is a tokeniser difference, not a
    prefill win. It is real for a user typing that sentence and it must not be
    quoted as a prefill result.

=====================================================================
3) WHAT THIS REPLACES
=====================================================================

docs/paper-evidence.md section 8 says "any claim about the vendor's runtime
speed measured here" is unsupported, because it had never been run. It has now:

  decode    charsiu 1.44x the vendor
  prefill   the vendor 1.23x charsiu per token, fixed costs within 8%

⚠ Still not supported by this round: anything about the vendor at the
frequency their benchmark.md was taken at. This is 594 MHz on both sides. The
vendor's device tree asks for devfreq over an OPP table reaching 800 MHz, and
Kiln's patch pins the clock instead, so neither side scaled.

⚠ And one board. Still one board.
