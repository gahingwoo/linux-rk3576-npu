round 401, 2026-09-13 — the fp16 attention arm crosses the CPU arm, and r400's
                        "no crossover" was a fact about the code

r400 section 3 measured the NPU attention arm at 1.19 to 1.23 times the CPU arm
over an eight-fold range of prompt length, FLAT, and concluded there is no
crossover length at head_dim 64. That conclusion was right about that binary
and wrong about the hardware. The ratio was flat because the fp16 path's per
element costs grew with the prompt exactly as the CPU arm's arithmetic does --
three of them on one core, and one of them doing work proportional to the
answer before the hardware was even asked.

  board     ROCK 4D, boot 2606ab9f, npu 594 MHz, cpu 2016/2208 MHz pinned
  binaries  /root/charsiu_run_sent  (one sentinel a row)
            /root/charsiu_run_pool2 (plus the pool on three per-op loops)
            /root/charsiu_run_auto  (plus CHARSIU_ATTN_NPU=auto)
  model     Llama-3.2-1B-Instruct-Q4_0.gguf, -c 1024, 852 token prompt
  arms      named in both directions, alternating, one warm-up discarded

=====================================================================
1. THE POISON WAS THE EXPENSIVE HALF, AND NOTHING HAD TIMED IT
---------------------------------------------------------------------
r400 short circuited the READBACK's 0xdeadbeef check. Its twin writes the
poison into every cell of every output before every submit, and that loop sat
in the one region of charsiu_fp16_matmul_group with no clock on it -- the
668 ms that r400 section 7 could only call `other`.

One sentinel a row instead. A job writes its whole output or none of it, so a
row whose first word survived is a row that was not written.

   tokens   every cell   poison+read    one a row   poison+read   TTFT ratio
   ------   ----------   -----------    ---------   -----------   ----------
      102          978            54          969            45        0.991
      302         2598           214         2542           155        0.978
      602         5584           636         5404           437        0.968
      852         8688          1130         8422           760        0.969

🏁 1) POISON + READ DOWN 33% at 852 tokens, text identical (md5 8b02145b), and
`other` went from 668 ms to 2. The point of naming a hole is that it stops
being one.

🔑 2) AND IT IS STRICTLY MORE INFORMATIVE. The every-cell form could only ever
answer "all of it is poison" or "not all", so a half written output was
accepted in silence. src/sentinel.h reports how many rows were never written;
tests/sentinel.c drives all three verdicts on six shapes, because a check that
has never been seen to fire is not a check and the hardware has never fired
this one.

three had never asked.

🏁 3) THE PACK IS 2.2x. Which also corrects r400 section 5: that paragraph
concluded a floor of 375 ms and "no amount of cleverness goes under it", from

⛔ 4) THE POISON BARELY MOVED, and that is the answer to what is left in it:

4. ⛔ THE OBVIOUS WAY TO SHIP IT IS WRONG, TWICE
---------------------------------------------------------------------
The crossover is a property of the WHOLE prompt, and attn_npu_layer sees one
chunk. The first implementation therefore tested each chunk's own running
position against the threshold, which looks strictly better -- CPU for the
early chunks, NPU for the late ones, best of both.

   852 tokens        CPU 8302   always on 7782
     MIN=128  7786     MIN=256  7911     MIN=384  7755     MIN=512  7844

⛔ 7) NO THRESHOLD BEATS SIMPLY BEING ON. The early chunks lose little and the
spread over the four thresholds (7755 to 7911) is wider than the best of them
is ahead. Per chunk selection buys nothing.

   202 tokens        CPU 1474   always on 1669
     MIN=128  1619     MIN=256  1584     MIN=384  1589     MIN=512  1582

⛔⛔ 8) AND AT MIN=512 EVERY LAYER IS REFUSED AND IT STILL COSTS 107 ms. A 202
token prompt never reaches 512, so that arm ran the CPU attention for all of
it -- and paid 1582 against the CPU arm's 1474. The K and V surfaces are
allocated and fed by attn_npu_append, which builds the mirror itself, whatever
attn_npu_layer decides.

🔑 9) A REFUSAL THAT LEAVES THE COST BEHIND IS NOT A REFUSAL. The decision has
to happen in attn_npu_get, before the mirror exists -- and it then needs the
length of the whole prompt, which nothing inside llama.c can see, because a
prompt arrives one chunk at a time and every function knows the running
position and none knows the total. llama_prefill_hint is the caller saying so.

6. A HANDLE EACH, BECAUSE THE SYNCS ARE CHARGED ON THE WHOLE BUFFER
---------------------------------------------------------------------
charsiu_fp16's `want` grows its five buffers and never shrinks them, and
charsiu_bo_prep/_fini are dma_sync over a WHOLE buffer object. One handle
serving both attention matmuls therefore sized every buffer for the larger
shape and synced that size for both: the scores group needs 393 kB of input
and paid for 5.2 MB, the values group needs 655 kB of output and paid for
8.6 MB. Thirteen times each way, four syncs a call.

   ⚠ THIRD TIME IN THIS TREE. Round 318 (the shared output buffer, 14 MB of
   cache maintenance a token becoming 280) and round 366 (per-device sizing,
   13.4 ms a token against 11.6) are the same sentence, and both notes live in
   npudev.c above code that does it right. npufp16.c never got the memo.

   attention  3.69 -> 3.24 ms a row      layer 2797 -> 2411 ms
   psync 212 -> 133   poison 323 -> 207   read 357 -> 292
   plan  136 ->  93   pack   239 -> 221   fence 925 -> 882

🏁 11) AND THE TWO STAGE TABLES SEPARATE, which is half the value:

     scores  176 submits, 1086 ms:  fence 496  read 245  poison 174  pack  44
     values  176 submits,  815 ms:  fence 386  pack 177  psync 116  read  47

The scores matmul is a readback problem and the values matmul is a pack
problem, and one table could not say that.

10. THE SOFTMAX REDUCES OVER THE ANSWER WHERE THE MATMUL LEFT IT
---------------------------------------------------------------------
A NULL Y has meant "leave it where it is" since this unit was written, and the
comment beside it says exactly why a softmax should use it: the caller reads
every one of those floats either way, so the copy out is a write and a second
read on top. The mirror copied anyway -- into a scratch of its own -- because
the values matmul reads the probabilities AFTER the next group call would have
released the buffer. Section 6's two handles made that false.

   attention  3.28 -> 3.00 ms a row      layer 2441 -> 2209 ms
   scores read 257 -> 10 ms
   scores plan 73 -> 146, because the release's fini on a HELD buffer is real
   work and it lands in that timer -- so the honest figure is 330 -> 156

🔑 19) AND THE PACK CAN ONLY READ IT THERE BECAUSE OF xtri0. The answer's rows
are npad apart, the values matmul contracts over kv, and kv > npad, so a pack
reading k elements a row would run off the end of every row into the next one.
It reads xtri0 + r <= pos + 1 <= npad. The causal triangle was worth nothing
when it was added (section 2 of r400) and is now load bearing twice over.

🏁 20) AND IT DELETES A TRAP. The scratch was [H][mmax][kv] and had to be
indexed by mmax and never by m -- a chunk with fewer rows than the last one
would land a row's tail on the previous chunk's probabilities, and every token
after it would attend to positions that are not in its prompt. A comment was
the only thing holding that off. The answers are laid out by the matmul's own
plan now: no stride here to get wrong, no 10.5 MB allocation, no inherited
tail.

13. THE SOFTMAX SCALE RIDES ALONG
---------------------------------------------------------------------
Attention wants softmax(x * scale) and took a pass of its own to get it --
read and write over rows that total 186 million floats at 852 tokens.
Multiplication by a POSITIVE constant is monotonic, so max(x * s) is
max(x) * s and the multiply folds into the exponential pass's existing load.

   softmax    458 / 463  ->  359 / 361 ms     (four passes a row become three)
   attention  3.00 / 2.99 -> 2.87 / 2.89 ms a row     layer 2206 -> 2109

🏁 24) BIT IDENTICAL, NOT MERELY CLOSE. The old form stored x[i] * s and read
it back, and an fp32 product is exactly representable in fp32, so the store
and reload changed nothing. Text identical to the CPU arm AND to the previous
build, worst relative error unchanged at 0.0086 -- and the CPU arm is the
right control here because it applies its scale inside attn_dot and was not
touched.

15. THE SENTINELS GO IN BEFORE THE RELEASE
---------------------------------------------------------------------
Section 25 said the obvious fold does not work, and named the shape that does:
write the sentinels once the values pack has finished reading the scores, so
the release's fini carries them and the next group skips a prep and a fini of
its whole 8.6 MB output buffer. That is a caller-side entry point,
charsiu_fp16_poison_and_release, because only the caller knows when it has
finished reading.

   scores group   907 / 914  ->  710 / 712 ms      poison 162 -> 24
   attention      2.88 / 2.86 -> 2.75 / 2.76 ms a row    layer 2107 -> 1996

🏁 27) PREDICTED 15 OF EVERY 16 AND MEASURED 165 OF 176. One shape per layer,
changing only when the chunk does: 11 chunks of 16 layers with the first of
each missing. The runtime counts it rather than the comment asserting it.

🔑 28) AND THE PREDICATE IS A TESTED FUNCTION, because it is the piece that
fails SILENTLY. If it says the buffer is still poisoned when it is not, the
readback finds live data, reports a healthy job, and reports exactly what it
would report for a healthy job -- the check stops being a check and no log
says so. charsiu_poison_matches in src/sentinel.h, seven cases in
tests/sentinel.c, including that offsets alone are not enough: a sentinel sits
at o[r * n] for r < m.

⚠ The values group reads 800 -> 885 because poison_and_release is called from
inside its timer. The honest pair is 1707 -> 1595. The scores handle is now
72% fence.
