round 400, 2026-09-13 — the fp16 activation pack halves with a vector
                        converter, and what is left of it is the STORE

r399 printed the counters this path had been keeping since it was written and
put the pack at 1357 ms of 2943 -- 46% of the fp16 attention path. The reading
taken from it, 235 ns an element, was wrong: it divided `pack` by `calls`, and
the two differ by a factor of the CONTEXT LENGTH, because attention's values
matmul contracts over k = kv and one head of one chunk is m*kv elements and not
m*head_dim. Fourteen instructions cannot cost 235 ns and that number sent this
round looking for a wall that is not there. `packel` is in the report now.

  board       ROCK 4D, boot 2606ab9f, npu 594 MHz, cpu 2016/2208 MHz pinned

  model       Llama-3.2-1B-Instruct-Q4_0.gguf, -c 1024, CHARSIU_ATTN_NPU=1

🏁 1) THE PACK HALVES AT EVERY LENGTH. 1132 -> 534 ms at 852 tokens, and the
saving is 1.92 ns an element at every one of the four (18/10.0M, 101/52.4M,
329/172.8M, 598/312M). TTFT -4.4% at 852.

🏁 2) TEXT IDENTICAL, 24 tokens, md5 8b02145b. It has to be: the conversion is
the same integer arithmetic four lanes at a time, and tests/pack_f16run.c walks
all 2^32 float bit patterns against the scalar definition on the desk. That
test was run against two deliberately wrong versions first -- the native
vcvt_f16_f32, which differs on 10.5% of floats, and an off-by-one on the flush
boundary, which differs on 0.4% and would survive any sampled check.

=====================================================================
2. THE CAUSAL TRIANGLE: convert the zeros, or memset them
---------------------------------------------------------------------
Row r of the probabilities has pos+1 entries that can be nonzero and zeros to
the end of k. The softmax wrote those zeros itself. Vector pack on in both.

   tokens   convert   pack     memset   pack   skipped   TTFT ratio
   ------   -------   ----     ------   ----   -------   ----------
      102       996     20       1005     18      40%        1.009
      302      2810     95       2747     88      36%        0.978
      602      6226    300       6190    271      35%        0.994
      852      9672    536       9660    494      31%        0.999

🏁 3) THE PROMISE HOLDS ON HARDWARE. CHARSIU_FP16_TRI_CHECK=1 at 852 tokens
read back all 98,114,560 elements it was told to skip: every one was zero.
Text identical, same md5 8b02145b.

⛔ 4) AND IT IS WORTH ALMOST NOTHING. Skipping 31% of the elements takes the
pack down 8%, and at no length does TTFT move outside its own spread (852:
9672 against 9660, spread +-150). The direction is consistent at all four
lengths, so it is not noise in the PACK column -- it is simply small.

🔑 5) WHY, AND THIS IS THE USEFUL PART: memset costs 72% of what converting
costs. At 602 tokens the triangle replaced 60M conversions with 60M memset
elements and saved 29 ms -- 0.48 ns an element, against 1.74 ns to convert one.
The arithmetic is not the cost. The MEMORY is: 312M elements is 1.25 GB read
and 624 MB written, and 534 ms of that is 3.5 GB/s, which is what one core
streaming through DRAM looks like.

⛔ THE FIRST VERSION OF THIS PARAGRAPH SAID 1.17 GB/s AND CALLED IT A
write-combining mapping. That counted only the bytes WRITTEN and then inferred
a hardware property from the number it left out. The read side is two thirds
of the traffic. Corrected before it reached section 12: the mapping is
ordinary cached memory, which section 7's readback confirms from the other
direction at 7.7 GB/s.

⚠ AND "ONE CORE" IS THE WORD THAT MATTERED. This paragraph concluded a floor
of about 375 ms and "no amount of cleverness goes under it" -- true only for
one core. r401 put the pack on the pool: 492 -> 228 ms. A bandwidth argument
that never names how many cores are spending the bandwidth is half an
argument.

⛔ 6) THERE IS NO CROSSOVER, AND THE REASON IS THAT THE RATIO IS FLAT. 1.19 to
1.23 over an eight-fold range of prompt length, with no trend. A fixed cost
would shrink as a fraction; this does not, so at head_dim 64 the NPU arm is
proportionally worse and there is no length at which it starts to pay.

🏁 7) THE OTHER HALF OF THE RULE IS NOT A LENGTH. r394's open question is
answered in the negative for head_dim 64: the rule cannot be "head_dim >= 128
OR a long enough prompt". Whatever selects the arm, it is head_dim.

🔑 8) THE PACK DID MOVE IT, JUST NOT FAR ENOUGH. Against the same CPU column,
the scalar-pack binary from section 1 sits at 1.256 / 1.266 / 1.300 / 1.266.
So halving the pack took NPU/CPU from about 1.27 to about 1.20 -- a real and
consistent 6%, and still the wrong side of 1.

6. ⭐ THE THING NOTHING WAS COUNTING: the softmax between the two matmuls
---------------------------------------------------------------------
With the clock pinned, the stage table says attention is 5.48 ms a row on the
NPU arm against 4.05 on the CPU arm, and charsiu_fp16_times accounted for
2129 ms of the 4669. The rest was a RESIDUAL, and this tree has called a
residual a measurement three times in one day before. So it got a clock.

   the loop, one core   1305 / 1308 ms
   the loop, pooled       466 /  488 ms      2.7x

It was a bare `for (h) for (r)` -- the one stage of this path with no pool
behind it, sitting between two that have one. Attention went 5.45 -> 4.46 ms a
row, reproduced on both repeats of an alternating A/B.

⛔ 10) AND REMOVING THE TRAILING ZERO LOOP WAS WORTH NOTHING. `for (t = pos+1;
t < npad; t++) sr[t] = 0.0f` is 58% of a row and the softmax's exponentials
are 14x it, so the stage stayed at 4.45/4.47. It is still the right code --
the pack memsets that tail anyway -- but the saving is not why.

🔑 11) THE ORDER THAT MAKES IT SAFE. The promise was verified on hardware
while the zero loop still enforced it (section 3), and only then was the
enforcement removed. Past pos the scratch now holds the RAW scores, so the
pack's memset is the answer rather than an optimisation. Text identical
between the CPU and NPU attention arms afterwards, md5 f50208bf.
