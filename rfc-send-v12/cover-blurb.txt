1/14 is Igor Paunovic's "[PATCH v2] accel/rocket: request the core clocks
by name", carried inside the series since v11 so that it applies to a
plain next-20260814 with nothing outside it to follow. It keeps his
authorship and its four tags. Tested on a Radxa ROCK 4D.

This adds the RK3576 NPU to accel/rocket, which today supports RK3588
only. The RK3576 carries two cores of the same RKNN block, wired up
differently. Two extra convolution buffer clocks, two power domains per
core, one reset rather than two, no NPU SRAM rail, and a PC_TASK_CON
that packs the task number into sixteen bits rather than twelve.

What changed since v11

Sashiko reviewed v11, which is what v11 was for. Most of what it found
is in the driver as it stands and not in this series; those are listed
at the end for Tomeu. Three things on this series changed:

  3/14   pm_runtime_get_if_active() has three answers, not two: 1 for
         active, 0 for suspended, and -EINVAL when runtime PM is not
         managing the device at all. The test was "> 0", so under
         CONFIG_PM=n the INTERRUPT_MASK write this patch exists to add
         never happened. It now tests for zero, the one answer that
         means the domain may be down, and puts the reference only when
         one was taken. Igor's Tested-by is kept; it is one condition,
         but say so if it should go.

  11/14  of_device_get_match_data() returns NULL for a device bound by
         name rather than by compatible, and core->soc was dereferenced
         two statements later. Checked, and the probe fails with -ENODEV.

  14/14  enables both cores and both IOMMUs. v11 enabled rknn_core_0
         alone, "left to whoever can test it". It has been tested.

One thing Sashiko raised on 4/14 that an argument does not settle.
pm_runtime_put_autosuspend() is asynchronous and the delay is 50 ms, so
on a workload whose gap between submits is shorter than that the domain
does not cycle after a reset, 10/14's reset pulse on power-on does not
fire, and rocket_core_reset()'s own resets are all that run. What I can
report: on the ROCK 4D both cores sit runtime-suspended at rest and, over
a run that decodes a 3.8B model for a while, accumulate 11.4 s active
and 17.8 s suspended in sysfs, so the domain does cycle under a real
workload. Whether it cycles after a timed-out job depends on the gap to
the next submit, as Sashiko says; I have not induced one -- that is a
kernel with JOB_TIMEOUT_MS lowered and a flash -- so the reset path
after a timeout is still an argument on my side, not a measurement.

Findings Sashiko labelled pre-existing, for Tomeu, all in code this
series does not touch:

  - the job completion path takes iommu_group_get(core->dev) and never
    puts it, one group reference a job (flagged on all nine mails);
  - the shared IRQ handler touches registers without checking the PM
    state;
  - runtime suspend has no synchronize_irq();
  - num_cores is used both as an array length and as the probe index;
  - rdev is leaked through devres on probe deferral.

Still open from v9, no reply since. 9/14 does three things: it adds the
settle delay, renames a macro, and gives RK3576_PD_NPU a regulator,
which also makes every RK3576 board force that domain off at probe. I
asked whether it wants splitting; Abel Vesa's Reviewed-by may be the
answer, and I would rather split it than have it merged on my silence.
And 13/14 gives each core both NPU domains, which is the description
that has been tested here rather than the topology; if it should be one
domain per core, 6/14's minItems has to change with it.

The bindings are unchanged since v9, where dt_binding_check was clean on
all three with dtschema 2026.6 and yamllint 1.38.0, and CHECK_DTBS was
clean on all 13 rk3576 and all 48 rk3588 dtbs.
